# AI 위임 루프 (AI Delegation Loop) · NanuriWeb 적용안

> 2026-10-02 · 출처: sdk-kim-builds.com / "AI 위임 루프 플레이북"
> 원칙: 에이전트를 매번 만들지 말고, **일 하나당 폴더 하나**를 만들고 매번 쓸수록 그 폴더가 좋아지게 한다.
> 이 문서는 그 원리의 요약 + NanuriWeb 사업 운영에의 적용 지도.

---

## 1. 핵심 원리 (한 문단으로)

AI의 지능이 모자라서가 아니다. **당신의 업무 지식이 글로 적혀 있지 않아서**다. 그러니 반복되는 일 하나마다 폴더 하나를 만들고, 그 폴더에 세 레이어를 둔다 — **프로세스**(판단 순서), **툴박스**(재사용 자산), **증명**(검증 항목). 매 실행마다 폴더가 조금씩 좋아진다. 채팅에서 고치지 말고 폴더에서 고친다.

### 세 레이어

| 레이어 | 파일 위치 | 무엇을 담는가 |
|---|---|---|
| **프로세스** | `SKILL.md` | 목적 · 언제 쓰는지 · 입력 · 번호 붙은 순서 · 결정 규칙 · 완료 정의 · 예외 |
| **툴박스** | `files/` | 스크립트 · 템플릿 · 참조 자료 · 톤 규칙 (일회성 산출물·비밀번호 제외) |
| **증명** | SKILL.md 안 검증 항목 | 외부 증거로 확인 가능한 5–10개 체크 ("괜찮아 보인다" 금지) |

### 피해야 할 안티패턴 5가지

1. **AI 인터뷰 없이 내가 직접 순서 적기** — 암묵적 판단이 누락됨
2. **모든 일을 한 폴더에** — AI 가 어떤 일인지 못 구분
3. **애매한 "언제 쓰는지"** — 실제로 치는 말 그대로 적어야 로드됨
4. **증명 레이어 생략** — 품질 관리가 결국 사람 몫이 되어 자동화 실패
5. **채팅에서만 고치기** — 다음 번에 또 같은 실수

## 2. 왜 NanuriWeb 과 정확히 맞는가

NanuriWeb 은 반복되는 사업 사이클이 명확하다:

```
문의 → 첫 답장 → 20문항 통화 → 제안서 → 계약 → 자료 수집 안내 → 초안 제작
→ 완성본 확인 → 검수 → 공개 → 인수인계 → 유지보수 → (뉴스레터로 관계 유지)
```

각 단계는 **매번 반복되는 일**이고, 매번 **살짝씩 틀리는 판단**이 있다. 지금은 그 판단이 목사님의 머릿속·대화 히스토리에만 있고, **글로 적힌 매뉴얼이 없다**. 그래서 매번 같은 설명·같은 수정이 반복된다.

폴더 기반 매뉴얼을 만들어 두면, 상담 50건이 쌓이는 사이에 매뉴얼이 50번 좋아진다. 50번째 상담은 1번째보다 분명히 수월하다.

## 3. NanuriWeb 에 당장 만들 폴더 5개 (우선순위 순)

예상 위치: `C:\...\02_NanuriWeb\operations\<폴더이름>\`
각 폴더 안 구조: `SKILL.md` · `files/` · `examples/` · `notes.md`

### 1️⃣ `church-intake-reply/` · 첫 문의 답장 (10분 안에 보내는 이메일)
- **왜 1순위**: 가장 자주 하는 일 · 그런데 매번 문구가 달라서 톤이 흔들림
- **입력**: 문의자 이름 · 교회/사업체/기관 이름 · 간단한 상황
- **툴박스**: `first-reply-template.md` (대괄호 자리표시자) · `twenty-questions.md` (04 스크립트) · `tone-rules.md` (존댓말·과장 금지)
- **증명 항목**: ① "문의는 문의입니다" 포함 ② 세 가지 질문만 ③ 300자 이내 ④ 다음 걸음 명시 ⑤ 서명 블록 일치

### 2️⃣ `church-proposal/` · 개별 교회 제안서 작성
- **왜 2순위**: 상담 뒤 가장 오래 걸리는 일 · 매번 가격·일정·포함 항목을 다시 짜 넣음
- **입력**: 상담 기록 · 교회 규모 · 요청 사항 · 자료 상태
- **툴박스**: 제안서 템플릿 (교회명·추천 디자인 3종·일정·가격이 자리표시자) · HebronGuide 자동 등재 안내 · 환불 조항 초안
- **증명 항목**: ① 세 상품 가격 모두 있음 ② 불포함 항목(도메인·결제 수수료 등) 투명 공개 ③ 추천 디자인 3종 · 각 "이런 교회에 잘 맞습니다" 한 줄 ④ 2주 일정표 ⑤ 교회 이름 오타 없음

### 3️⃣ `onboarding-pack/` · 계약 뒤 자료 수집 안내
- **왜 3순위**: 매번 "뭘 보내 드리면 되나요?" 질문이 반복됨
- **입력**: 교회명 · 자료 상태 · 담당자 이름
- **툴박스**: 체크리스트 (05 1페이지 소개서 안 체크리스트) · 자료 업로드 폴더 안내 · 사진 촬영 팁 · 인사말 초안 예시
- **증명 항목**: ① 로고·사진·연락처·시간·주소 모두 있음 ② "없어도 시작합니다" 안내 ③ 자료 업로드 폴더 링크 ④ 다음 걸음 날짜 명시 ⑤ 24시간 안에 질문 받는다 명시

### 4️⃣ `biweekly-newsletter/` · 격주 뉴스레터
- **왜 4순위**: 아직 시작 전이지만 시작 즉시 반복 · 톤 흔들림 위험 큼
- **입력**: 이번 2주의 에피소드 1개 (상담·제작·공개 중 하나)
- **툴박스**: 뉴스레터 템플릿 (제목·열기·본문·마무리 자리표시자) · 금지 표현 ("결국 ~입니다" 등) · 성경 구절 인용 규칙
- **증명 항목**: ① 500자 이내 ② 실제 에피소드 1개 (추상적 교훈 금지) ③ 결론 다 내리지 않고 여백 남김 ④ 구독 해지 링크 ⑤ HebronGuide 큰 그림 1문장

### 5️⃣ `handoff-package/` · 공개 뒤 인수인계
- **왜 5순위**: 공개 직후 교회가 가장 불안한 지점 · 한 번 매뉴얼 만들면 평생 쓸 수 있음
- **입력**: 교회명 · 도메인 · 관리자 계정 · 완성 자료 목록
- **툴박스**: 관리자 화면 사용 안내 3개 동영상 · 월 유지보수 안내 · 데이터 인계 보장 문구 · 1개월 후 체크인 이메일 템플릿
- **증명 항목**: ① 관리자 계정 안전 전달 (별도 채널) ② 짧은 영상 3개 링크 ③ 자료 인계 보장 서면 ④ 긴급 연락처 ⑤ 1개월 뒤 체크인 날짜 캘린더 등록

## 4. 각 폴더의 뼈대 (복사해서 쓰는 템플릿)

```
operations/<폴더이름>/
├── SKILL.md
├── files/
│   ├── INDEX.md
│   ├── <template>.md
│   ├── <reference>.md
│   └── tone-rules.md
├── examples/
│   └── (처음엔 비어 있음 · 첫 실행 때 좋은 결과 저장)
└── notes.md
```

### SKILL.md 템플릿

```markdown
# [폴더 이름 · 사람이 읽는 설명]

## 목적
한 줄로.

## 언제 쓰는지
실제로 치는 말 그대로. 예: "교회 첫 문의 답장 써줘"

## 입력
- 어디서 올까
- 어떤 모양일까

## 순서
1. 먼저 …
2. 그 다음 …
3. 결정: X 면 Y, Z 면 W
4. 마지막 …

## 완료의 정의
아래 증명 항목이 모두 통과하면 완료.

## 증명 항목 (외부 증거로 확인 가능해야 함)
- [ ] 항목 1 (근거)
- [ ] 항목 2 (근거)
- [ ] 항목 3 (근거)
- [ ] 항목 4 (근거)
- [ ] 항목 5 (근거)

## 예외 사례 (과거 실패에서 배운 것)
- (처음엔 비어 있음)

## 사용할 툴박스
- `files/<template>.md` — 자리표시자 템플릿
- `files/<reference>.md` — 참조 자료
- `files/tone-rules.md` — 톤 규칙
```

### notes.md 템플릿

```markdown
# 수정 기록 (최신이 위)

## YYYY-MM-DD · [무엇이 잘못됐는가] → [무엇을 바꿨는가]

- 무엇이 잘못됐는지 한 줄
- 어느 레이어 실패인지 (프로세스/툴박스/증명)
- 어느 파일을 어떻게 바꿨는지
```

## 5. 루프 돌리는 법 (매 사용 뒤 5분)

1. **AI 결과물에 오류가 있었나?** → `notes.md` 에 기록 (날짜·무엇·무엇을 바꿨는지)
2. **같은 오류가 두 번째인가?** → 부드러운 리마인더가 아니라 **명시적 규칙**으로 변경 (SKILL.md 또는 tone-rules.md)
3. **좋은 결과물이 나왔는가?** → `examples/YYYY-MM-DD-good.md` 로 저장. 다음에 AI 가 참조함.
4. **월 1회 `notes.md` 검토** → 반복되는 수정 = 다음 자동화 대상

**이 루프의 핵심**: 채팅에서 "다시 해줘" 하지 말고, 매뉴얼을 고쳐라.

## 7. 나중에 생각할 응용

- **nanuriweb-edit 스킬 자체도 이 틀로 다시 정리** — 이미 `.claude/skills/nanuriweb-edit/SKILL.md` 가 있으나, "증명 항목"(배포 전 체크리스트)이 암묵적. 명시적 5개 체크로 격상하면 배포 사고 확률 감소.
- **church_templates/ 안 디자인 10종** 도 각각 "작은 매뉴얼" 로 가질 수 있음 (톤·구성·사용처·완료 정의) — 디자이너·외주 작업자가 생겼을 때 바로 넘길 수 있는 자산.
- **HebronGuide 자동 등재 안내** 도 반복 문구이므로 `files/hebronguide-blurb.md` 하나로 모든 문서가 참조하게 하면, 한 곳만 고치면 모든 자료가 동기화.
